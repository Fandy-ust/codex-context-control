# Codex Context Control

在 macOS 上，为每个 Codex 聊天单独设置上下文窗口和自动压缩阈值。

包含原生控制面板、Codex 连接桥接、Hook stats 状态输出，以及可重复执行的安装/卸载程序。使用原有 Codex 登录和运行时，不需要为本工具配置 API key。

**当前版本：0.9.1，本地预览版。已验证 Codex 0.159.2 和 0.160.0。** 窗口与压缩阈值均使用滑条，按 1K 调整；窗口变化时压缩阈值按比例联动。照常打开 Codex 后，菜单栏自动出现 **「上下文」**，点击即可打开设置。未验证的运行时仅透传，不执行预算调整。0.5.2 增加 fork 预算继承，并保留连续调整时下一轮前优先完成最新预算的修复。

## 提前压缩修复（0.9）

侧栏提供「提前压缩修复」开关，**默认关闭**。它选择独立存放的修复版 Codex 运行时，解决部分跨轮推理请求中重复补算历史推理导致的提前压缩。实际请求用量和费用仍按服务器报告计算。

修复基于 [coinman-dev 的社区补丁](https://github.com/coinman-dev/codex-context-accounting-fix)，源码提交、补丁提交和校验值锁定在 `runtime-patches/manifest.json`。这是社区修复：它假定 Responses Lite 的跨轮推理已包含在服务器用量内，不代表 OpenAI 已确认所有服务路径都遵守这一约定。

首个包针对 Apple Silicon macOS 和 **Codex 0.160.0**。开关只影响下一次启动的 Codex 运行进程；当前进程继续使用原版，界面会显示待生效。开启或关闭后，须完全退出并重新打开 Codex；仅关闭聊天窗口不会更换运行时。关闭后即恢复原版。Codex 更新到其他版本、修复包缺失或文件校验失败时，后续启动自动使用原版。安装过程不会修改 ChatGPT.app，也不会修改已有登录信息。

准备修复包：

```sh
# 在装有 Rust/rustup、Git 和 Xcode 命令行工具的 Apple Silicon Mac 上构建。
node scripts/build-patched-runtime.mjs
node scripts/install-patched-runtime.mjs build/patched-runtime
```

也可以在本私有仓库运行 `patched-runtime` GitHub Actions 工作流，下载它生成的 macOS artifact 后安装。下载 artifact 后须恢复 `codex` 文件的执行权限（`chmod +x`）。工作流编译固定版本的上游源码，并执行本机模拟计数测试及桥接兼容性测试；不使用账户凭据，也不调用远程模型。它不自动发布、安装或启用修复。常规安装／重新安装保留用户的开关选择。

安装时会从同版本的现有桌面 App 复制代码执行宿主、搜索、语音／shell 等辅助文件到独立目录，并校验文件。保留原生 `bin`、`codex-path`、`codex-resources` 布局，避免移动核心程序后找不到工具；无需再次下载这些辅助文件。

修复包保存在 `~/Library/Application Support/CodexContextControl/runtimes/`，开关保存在同目录的 `runtime-fix.json`。文件签名、SHA-256、源码版本和补丁标识在安装时校验；运行时选择会再次校验文件并检查宿主 Codex 版本。

## 软件形态

| 组成 | 使用方式 |
| --- | --- |
| **Codex Context Control.app** | 选择聊天、拖动窗口/压缩滑条、预检和提交 |
| **菜单栏「上下文」** | 随 Codex 接入自动出现，显示连接状态并提供设置入口 |
| 自动接入登记 | 让原来的 Codex 图标启动时自动载入连接桥接，无需另开启动器 |
| 本地控制服务 | 保存逐聊天预算，在轮次之间安排应用 |
| Stop hook | 将当前聊天的预算和应用状态显示在原生 Hook stats 中 |

窗口切换会暂时卸载并恢复**同一个聊天**，保留聊天 ID 和历史；不会重启整个 Codex 应用。正在生成的请求继续使用旧设置，调整在轮次之间执行。

## 快速部署

需要 macOS 14+、已安装的 Codex/ChatGPT 桌面应用、Node.js 22.13+，以及 Apple Command Line Tools（提供 Swift 编译器）。安装时会下载并随应用打包本地分词器 js-tiktoken；统计过程中不联网。

```sh
gh repo clone Fandy-ust/codex-context-control
cd codex-context-control
npm run install:local
```

私有仓库需要先完成 GitHub 登录。也可使用 GitHub 提供的仓库下载方式取得源代码，再执行安装命令。

安装程序编译原生面板，在 `~/Applications` 创建一个设置应用，将服务代码放到 `~/Library/Application Support/CodexContextControl`，登记当前用户的自动接入，并向现有 `~/.codex/hooks.json` **追加一条自己的 Stop hook**。会先备份该文件，保留其他 hooks，不修改全局窗口配置，也不修改签名的 Codex 应用。升级时移除旧的专用 Launcher。

自动接入使用当前用户 GUI 登录会话的 `CODEX_CLI_PATH` 和一条登录登记任务。登记任务执行后退出；控制服务由 Codex 的运行时按需启动。该变量属于用户会话范围，其他读取它的工具也能看见；桥接只对识别到的 Codex 桌面调用启用，其他调用透传已配置的运行时。已有其他自定义值时停止登记，不覆盖；卸载时恢复本项目仍持有的设置。详见 [架构与接入](docs/ARCHITECTURE.md)。

### 首次接入

1. 完成本轮工作，然后正常退出原有 Codex/ChatGPT 桌面客户端。
2. 照常从 Dock、Spotlight 或应用文件夹打开原来的 Codex/ChatGPT。
3. 在原客户端打开一个已有聊天，进行正常的一轮交互，让工具读取实际窗口与最近请求用量。
4. 点击菜单栏 **「上下文」→「打开上下文设置…」**，选择聊天，预检并提交预算。关闭窗口后，菜单栏入口和预算控制继续工作。
5. 在正常的下一轮请求后，状态从“等待下一轮确认”变为“窗口已确认”。工具不会为确认设置而额外发送提示词。

需要在 Codex 的 `/hooks` 中审核并信任新增的 **Context Control** hook，才会显示相应 Hook stats 文字。未审核时，原生控制面板及预算控制仍能工作；安装程序不会生成或伪造信任记录。

首次退出/重新启动是为了让新进程取得自动接入配置。以后直接打开原来的 Codex 即可，调整预算无需重启整个客户端，也无需先打开控制面板。

## Fork 继承

正常 fork 已启用独立预算的对话时，创建请求直接带入父对话的窗口、压缩阈值、预留和保留下限。相同模型下，父对话为 363K，分支的第一轮也使用 363K。每个分支保存独立副本；后续修改父对话不会联动已有分支，再次 fork 会继承直接父分支的设置。没有独立预算或已停止自动应用的父对话保持原生默认行为。

## 调整例子

把窗口滑条调到 **700K**，选择 **90%**，压缩滑条即为 **630K**。把窗口改成 **400K**，压缩阈值自动变成 **360K**。两条滑条均按 **1K** 步进，旁边的 − / ＋ 可逐 K 微调；单独拖动压缩滑条会更新联动比例。保留 80%、85%、90% 快捷选择。

工具自动反算底层配置：在 95% 模型上，700K 对应底层 `736,843`，运行时取整后读回 **700,000**。当前模型最多可用多少，也按可用容量显示。滑条上限按模型目录和原生压缩规则计算，向下取整到 K。按比例联动时阈值也向下取整到 K，预览的 K 值就是提交值。下一轮预留和手动保留下限放在“高级设置”。

工具分别展示：

- 输入的目标可用窗口和按比例计算的压缩阈值；
- 运行时真正上报的可用窗口；
- 最近请求用量（当前占用的近似值）。

旧预算原样保留；面板按其实际可用容量显示，例如旧底层 700K 会显示为可用 665K。只有点击应用后才提交新的预算。旧值若不是整数 K，滑条草稿会向下取整到 K；顶部已保存预算仍显示原值。底层整数换算可在高级设置中查看。

“已保存”“已重新加载”“下一轮窗口已确认”是不同状态。接口返回成功，不代表窗口已改变。

| 能力 | 0.9.1 |
| --- | --- |
| 逐聊天窗口、压缩阈值及预算持久保存 | 已实现 |
| fork 预算继承 | 创建时复制父对话预算；分支与父对话随后独立调整 |
| 双滑条、1K 微调、所见即所得与比例联动 | 已实现；自动反算底层预算 |
| 普通应用图标启动后自动接入 | 已实现；首次安装后正常重开一次 |
| 随 Codex 自动出现的菜单栏入口 | 已实现；可查看连接状态和打开设置，不自动弹出大窗口 |
| 生成中的调整排队 | 已实现 |
| 缩小前容量、预留和手动保留下限检查 | 已实现，基于可观测用量估算 |
| 同一聊天重新加载、恢复历史与执行设置 | 已验证上述两个运行时版本 |
| Hook stats 状态展示 | 已实现；需用户审核 hook |
| Hook stats 内嵌滑块/输入框 | 原生界面没有该扩展接口；使用独立原生面板 |
| 精确预测压缩后剩余 token 数 | 无法保证，必须压缩后重新测量 |
| 调整 95% 可用比例或突破 total 的 90% 规则 | 未实现，不改这些规则 |
| 修改服务端真实最大上下文 | 不支持 |
| 其他宿主、云端会话、父代理管理的子会话、临时会话 | 不支持 |

本工具不通过删除聊天记录缩减上下文，不把全局累计 token 当作上下文占用。最近请求用量也不等于内核的全部上下文估算，因此预检不能保证后续原生压缩绝不触发。

## 上下文详情与响应图表（0.6）

打开菜单栏「上下文」，选择聊天，点击预算页中的「上下文详情」。无需另开浏览器。

- 分类明细表：工具调用、工具返回、用户消息、最终回复、进度说明、指令与摘要，以及其他／未分项，展示 token 估算与条目数。0.6.4 移除了分类柱状图，保留明细表与趋势图。
- 按事件着色的节点曲线：每次模型响应的观测输出速度。悬停显示输出、推理生成量、缓存命中／写入、相对上次命中的变化及当时的模型配置；也可用下拉框选择没有计时的响应。
- 缓存趋势：输入总量与缓存命中。缓存属于输入的子集，不叠加到上下文占用中，也不会改变 Codex 缓存策略。
- 自动刷新每 10 秒运行一次，关闭详情页即停止；可手动刷新。统计结果短暂缓存在本机内存中，不保存消息正文。

分类是最近一次已记录请求开始前的快照。可见文本使用 `o200k_base` 估算；其他／未分项是输入总量减去可见估算，含图片、推理、工具定义和估算误差，不等同于精确思维链用量。明文压缩摘要只计一次，不透明压缩内容合并到其他。

速度 = 运行时报告的输出 token /（首个生成项目开始到该响应用量记录的时长）。包含推理、正文和工具参数生成，不包含后续工具执行；不是严格的服务器解码速度。没有首项开始时间的记录显示暂无计时，不补零。一轮用户消息可能产生多个模型响应，图表按响应分点。响应图只画本聊天自己的记录；上下文分布包含继承的保留历史。

配置只显示日志明确记录的标量字段：模型、推理强度、服务档位、可用窗口。缺失字段（包括尚无历史记录的压缩阈值）显示未记录；不拿当前预算回填过去。整个详情服务在本机读取所选聊天及其继承历史，不调用模型或外部服务。详见 [隐私说明](docs/PRIVACY.md)。

### 对话事件与 steering（0.6.2）

时间线、速度图与缓存图共享同一条记录顺序轴（不是等长时间刻度）：浅灰为中间响应、蓝色为最终回复、绿色菱形为用户输入／追加输入、紫色方形为压缩完成。没有计时的响应仍出现在事件轨道；输入与压缩事件不伪造速度值。缓存图另以紫色虚线标记压缩完成位置。悬停事件或用下拉框可查看用户文本 token 估算、图片数、轮次及压缩后的保留项目数。

追加输入以同一轮内已有用户输入或模型输出为依据标识；缺少轮次信息时只显示普通用户输入，不猜测 steering。环境注入、压缩摘要及 UI 的重复消息事件不会计作用户输入。压缩响应仅按压缩记录的 `compaction_response_id` 关联；缺少关联的响应不会仅凭缓存下降被猜作压缩。

在核对的 Codex 0.160.0 源码中，steering 使用 `TurnInput::UserInput` 排入活动轮次的待处理队列，采样循环在可接收时取出并记录。它与 `FunctionCallOutput` 是不同输入类型，可以同批提交给模型，但用户内容仍作为独立用户消息保留，不是拼接到工具输出正文里。

源码依据：[steering 入队](https://github.com/openai/codex/blob/a956835d020762cb2b570053af06f643a11c0ecc/codex-rs/core/src/session/turn_input.rs#L695)、[取出待处理输入](https://github.com/openai/codex/blob/a956835d020762cb2b570053af06f643a11c0ecc/codex-rs/core/src/session/turn.rs#L426)、[用户消息的持久化](https://github.com/openai/codex/blob/a956835d020762cb2b570053af06f643a11c0ecc/codex-rs/core/src/session/mod.rs#L4963)。

### 紧凑联动视图（0.6.3）

趋势区按「输出速度 → 输入与缓存 → 对话事件 → 事件详情」紧邻排列，共享横轴，只在最下面显示刻度。鼠标悬停同步定位三层图，点击可固定所选事件；下拉框仍可选择任意记录。默认详情保留速度、输出量、输入量、缓存命中、命中变化、命中率及一行模型配置；推理量、写入量、完整轮次等放在「更多信息」。解释文字收进「统计说明」，图表用于对照趋势，不从单个趋势自动推断因果。

### 活跃上下文与 API 费用估算（0.7）

顶部仅显示最近请求的「活跃上下文」及其「缓存命中」，不是容量上限。下方费用卡累计当前聊天自己的已记录请求，包括压缩响应；分支不会重复计入父聊天已经发生的费用。计价明细显示普通输入、缓存读取、缓存写入、输出的 token 总量及各自费用；时间线「更多信息」也可查看单次费用。

价格快照核对于 2026-10-16，随版本打包在 `src/api-prices.json`，来源为 [官方 API 价格](https://developers.openai.com/api/docs/pricing)，不是 ChatGPT 套餐扣费或实际账单。支持表内 GPT-6 Astra、GPT-6.1 Sol、GPT-6 Sol、GPT-6 Luna 与 GPT-5.6 Sol/Terra/Luna 的已核实档位。未知模型或未列出的费率不推测；价格快照不会后台自动联网更新。

面板费用统一按每次请求所用模型的 **Standard 基础单价**估算，不计算 Fast 等加速溢价。总额、四项明细、模型小计和单次响应使用相同口径。实际模型配置独立保留，显示为 `GPT-6 Astra · High · Fast`；`priority`/`fast` 显示为 Fast。未指定档位不影响基础价格估算，未知模型或缺失用量仍不计入。生成开始后配置变化不会回填此前响应。

每次费用公式（单价为 USD/百万 tokens）：

```
普通输入 = 输入总量 − 缓存读取 − 缓存写入
费用 = (普通输入 × 输入价 + 缓存读取 × 缓存价
       + 缓存写入 × 写入价 + 输出 × 输出价) / 1,000,000
```

缓存写入优先使用运行时报告的非零值，否则按未命中输入估算，不能用命中量差值代替。输出已经包含推理，不能再加一次。输入超过 272,000 tokens 时，整个请求采用对应的长上下文费率，与用户设置的窗口容量无关。缺失计数、缓存计数超过总输入、未知模型都不计入已估金额，界面显示覆盖率及未计入原因，不将未知作为零费用。

面板不再显示 Fast 价格对比。所有金额不含工具独立收费、税费、地区/FedRAMP 加价或组织协议折扣。缓存公式依据 [官方缓存文档](https://developers.openai.com/api/docs/guides/prompt-caching)，服务档位依据 [Fast 文档](https://developers.openai.com/api/docs/guides/fast-mode)。

### 缓存写入零值的来源（0.7.1）

核对 Codex 0.160.0 源码发现，原始 API 用量中的 `input_tokens_details.cache_write_tokens` 缺失时，会由 `#[serde(default)]` 转成零，再写入 `TokenUsage.cache_write_input_tokens`。本地 `TokenUsageRecord` 没有保留原始字段是否存在，因此零值不能证明服务端确实报告了零次写入，也不能证明缓存写入免费。源码包含非零写入量的解析测试，说明该版本能够读取非零字段。

[解析和默认值](https://github.com/openai/codex/blob/a956835d020762cb2b570053af06f643a11c0ecc/codex-rs/codex-api/src/sse/responses.rs#L128)；[非零值测试](https://github.com/openai/codex/blob/a956835d020762cb2b570053af06f643a11c0ecc/codex-rs/codex-api/src/sse/responses.rs#L802)。

0.7.1 曾将这类零值标为未确认。0.7.2 已用原始用量通知完成真实测试，并改用下面的 API 等价区间。

### 原始响应验证与官方公式（0.7.2）

已使用 GPT-6.1 Sol、GPT-6 Astra 各三次真实 ChatGPT 登录请求，确认原始响应明确返回缓存写入 0，同时缓存读取增长。另用已安装运行时完成缺失／零／非零的三组本机对照，排除了“运行时无法读取非零值”的解释。[完整研究与复现步骤](docs/CACHE-WRITE-RESEARCH.md)。

Codex credits 官方不单独收写入费，不能把这条通道的零计量当作没有物理缓存增长。主金额严格使用 OpenAI 官方 `calculateInputCost` 的输入分拆公式、上游返回用量及公开单价，再加输出费用，不把用户猜测或缓存读取增量计作写入。原始记录的四类用量和费用可分别核对。额外写入的上下限仅放在折叠的「写入假设分析（非官方计量）」中，不替代主金额或实际账单。

### 缓存写入估算（0.7.3）

按用户选择，缓存写入直接展示估算数字，不再展示“上游计量零”等说明。未报告非零写入量时，按「输入总量 − 缓存读取」估算新增写入（偏保守）；非零报告值仍使用原值。采用官方互斥计费公式重算四项，估算写入从普通输入中扣除。总额、分类费用、模型小计以及单次响应费用保持一致。原始日志数字不修改，估算方法放在折叠明细中。

### 缓存与计时的数据质量（0.7.4）

趋势图改称“生成速度”，明确不含生成前的等待。更多信息显示最近输入记录到生成开始的间隔估算。缺失计数保留为空并断开折线；无原始响应证据的日志零值以橙色空心点标记，不自动视为已证实的缓存未命中。缓存超过输入或时间戳反序等无效记录不用于计量。[截图异常的逐请求核查与本机对照](docs/CACHE-SPEED-RESEARCH.md)。

### 统计与界面性能（0.8）

- 后台计算线程复用，按需最多两路并行；同聊天并发请求合并，不堆叠重复任务。闲置 60 秒释放工作线程。
- 原生日志按完整行增量读取；未完成的 UTF-8 行等写完再处理。替换、截断和同大小修改会重读，手动刷新完整重验。分支继承仍严格遵守原始字节/条目边界。
- 文本 token 数按内容哈希缓存；已有消息无需反复分词。工作线程最多缓存 4 个日志片段、合计 64 MiB 源数据和 20,000 个 token 计数，超出淘汰。
- 数据未变直接返回相同聚合结果；界面不会重复解码和重建图表。自动检查仍为 10 秒，统计详情独立于预算页两秒状态轮询。
- 图表数据与鼠标选择分离；悬停只更新游标和详情，索引提前生成，定位使用二分搜索。选择和固定交互保持可用。
- 模型目录按文件版本缓存，修改后自动失效，不反复读取同一份 JSON。

本机约 31 MB、4,484 条记录的聊天，旧版每次完整统计约 0.73–0.81 秒；改进后无变化刷新约 3–12 ms，手动重读并复用 token 缓存约 68 ms（具体随记录量/机器变化，首次仍需完整分词）。100 次悬停选择加固定操作测试中，图表主体构建次数保持为 1。正确性测试比较增量和完整重算，覆盖追加、半条记录、压缩、替换、分支边界、并发与错误恢复。

复现后台测量：`node scripts/benchmark-statistics.mjs <chat-id>`。只打印时间、计数和缓存指标，不输出聊天正文。[缓存与隐私](docs/PRIVACY.md)。

### 原生 fork 补充继承（0.9.1）

桌面端创建分支时，即使没有经过连接桥的 fork 请求，也会从本地会话首条元数据的 `forked_from_id` 识别真正的父聊天，复制其已启用预算并保存。读取以 1 MiB 为上限，缓存首条元数据，不扫描对话正文；不会把 `history_base` 指向的更早祖先误当成父聊天。已有分支预算（含手动停止自动应用的预算）不覆盖，后续父聊天改动不联动。连接桥收到预算后会自动应用；正在生成的聊天等待轮次结束，缺少用量时等待一次有效观测，读回后才标记窗口已确认。

侧栏使用独立于标题栏的可拖拽双栏布局，连接状态以绿色／灰色圆点表示。后台发现继承预算后，未编辑的滑条会自动同步，不再停留在默认预设。
