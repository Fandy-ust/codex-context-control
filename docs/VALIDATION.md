## 1M 窗口可行性：2026-10-16

`node scripts/probe-context-ceiling.mjs` 使用原版 0.160.0 可执行文件、独立临时目录和本地模拟响应验证原生窗口读回。三个测试均通过，没有改写真实配置或聊天。

| 模型目录上限 | 可用比例 | 配置窗口 | 实际原生读回 |
| --- | --- | --- | --- |
| 872,000 | 95% | 1,052,632 | 828,400 |
| 1,050,000 | 95% | 1,050,000 | 997,500 |
| 1,050,000 | 100% | 1,000,000 | 1,000,000 |

源码 `models-manager/src/model_info.rs::with_config_overrides` 将配置窗口限制到目录的 `max_context_window`，随后 `usable_context_window` 应用比例。官方配置支持启动时加载 `model_catalog_json`，所以覆盖本地目录可以解除这层限制，不必重新编译核心。该路径仍需处理 App 自身上限校验与运行时启动时的目录快照，不能只改面板数字。

官方 [GPT-6 Astra 模型页](https://developers.openai.com/api/docs/models/gpt-6-astra) 列出 1,050,000 总上下文和 128,000 最大输出；这不能直接证明 ChatGPT 登录的 Codex 服务具有相同输入接受边界。保留 95% 时，精确 1M 可用需要 1,052,632 的底层窗口，已略高于上述公开总窗口，不应为凑整数直接采用。`total` 自动压缩阈值还被原生限制在底层窗口的 90%；解除目录限制不会同时解除这个阈值。

测试仅使用短提示和模拟 token 用量；报告的 `serverCapacityVerified` 为 `false`。尚未向真实服务发送百万 token 输入，也未在用户聊天启用扩展。

用户报告原生 UI 仍为 828K。读取实际连接确认：目标 920,000、配置窗口 1,022,223，但原生读回 828,400；并非 UI 格式化问题。生成目录中的 Astra 上限和比例正确，实际运行进程也包含目录参数，但桌面在 `app-server` 后另带一组 `-c`。补入相同的前后两组参数后，原版运行时集成测试稳定复现失败。此前 0.12 测试只覆盖了单组参数，未覆盖这个真实桌面调用形态。

修复将调用方的全部配置覆盖合并到子命令之后，再追加目录与容量设置，保持其他桌面参数。新集成测试先读取 `config/read` 核对目录路径、窗口、子命令前后的配置均被保留，再验证原生窗口读回 **920,000**、自动压缩和大输入保护。测试通过。

控制服务区分修正前的连接，标记需要重开并拒绝对该连接继续提交预算；面板和菜单调节同步禁用，避免再次接受无法生效的 920K。未加载聊天保留已换算预算的显示比例。

## 0.13：新对话全局默认

全局默认窗口／压缩阈值保存在控制服务自己的状态文件，初始为 920K／904K。新建用户聊天在 `thread/start` 发给原生运行时之前读取最新设置并注入配置；创建成功后保存为该聊天独立预算，保留当时的全局修订号。设置读取后即使全局再变化，正在创建的聊天仍使用同一份快照。

- 原版 0.160.0 配合本地模拟服务验证：新聊天第一轮读回 500K；同一进程内将全局默认改为 800K 后，新聊天第一轮读回 800K，原聊天及其 fork 仍读回 500K。
- fork 使用父预算；没有父预算时保留原生继承行为，不给 fork 注入全局默认。恢复旧聊天、临时工具会话及明确标记的代理会话不读取全局默认。
- 默认值接口验证身份与来源，拒绝越界、非 1K 精度、余量不足和过期修订写入；验证保存后可重新读取，已有预算没有被改写。
- 原生设置窗口提供双滑块及「使用当前聊天设置」。已检查原生渲染，只有进度条在最大档显示紫色渐变。
- 回归 86 项：83 通过、3 项可选跳过；另针对默认值与实际原生创建／fork 路径的五项验证通过。全部模型响应来自本地模拟服务，没有消耗真实模型额度。

已运行的旧桥接不支持新建聊天拦截时，界面明确提示需要一次完整退出／重开。更新后的桥接在每次创建新聊天时动态读取默认值，因此之后保存全局默认无需重启。
