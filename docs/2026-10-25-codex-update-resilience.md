# Codex 后续更新的兼容性防护研究

日期：2026-10-25（Asia/Taipei）

范围：`codex-context-control-lzma2`；Windows 与 macOS

状态：研究与实施建议，尚未实现。此次只新增本文档，不修改代码、安装、启动配置或发布版本。

后续进展：用户随后授权开发，0.26.6 工作区已实现命令保守识别、共享隔离握手与配置读回、运行时身份缓存、失败冷却/原生启动及断连诊断。实施范围与实际验证见 [0.26.6 开发说明](releases/0.26.6.md)。下文保留研究时的现状描述；未覆盖的建议仍属后续工作。

## 结论

优先目标应是：**Context Manager 的增强功能失去兼容性时，Codex 仍可使用原生运行时正常启动。** 不能保证未来上游更新永远不出问题，但可以降低接入层把兼容性变化放大成整个客户端无法启动的概率。

本次记录指向 Codex 桌面启动命令、协议包装和进程生命周期的兼容性，并未证明是 GPT 模型本身更新导致。后续应分别应对三类变化：

| 更新层 | 主要风险 | 对应防护 |
| --- | --- | --- |
| Codex 桌面版与内置 CLI | 新启动子命令、参数、运行时路径、父子进程关系 | 未知命令透传、运行时身份检查、真实桌面启动验收 |
| app-server 协议与配置 | 字段、事件、配置语义、握手和连接方式变化 | 能力验证、契约差异检查、分功能降级 |
| GPT 模型与目录 | 新模型标识、上下文能力和元数据变化 | 使用实际模型能力，未知模型保持原生设置，不套用旧模型上限 |

原故障证据及不确定性见 [启动故障分析](2026-10-25-codex-startup-policy.md)。本文不把当次一定调用了 `proxy` 当作已证实事实，也不把文档所述定向测试等同于桌面修复已验收。

## 当前代码已经具备的保护与缺口

以下是本次读取工作区的结果，包含工作区内原有、尚未提交的 0.26.5 修改，不代表已安装版本的行为。

| 位置 | 当前行为 | 更新后的剩余风险 |
| --- | --- | --- |
| `src/compatibility.mjs` | 排除 `proxy`、`daemon`、`help`、生成代码等命令；识别 stdio listen 地址 | 仍以排除列表为主，未来未知子命令可能误入包装；在整个参数数组搜索单词也可能把选项值当命令 |
| 同上 `runtimeSupported()` | 接受符合 `codex-cli x.y.z` 格式的输出 | 只能识别运行时身份格式，不能证明新版本协议及增强功能兼容 |
| `src/wrapper.mjs` | 非桌面、非 stdio 或版本格式不认识时透传；管理服务连接失败会重试 | 已有透传基础，但已识别版本仍直接进入增强路径；准备目录、参数注入和桥接仍可能影响启动 |
| `src/runtime-lifecycle.mjs` | EOF 后先关闭输入；默认等待 30 秒，再进入终止清理；其他断连触发清理 | 日志未区分断连触发源；30 秒是当前默认值，不是上游保证的协议期限 |
| `src/platform/windows-probe.mjs` | 使用隔离目录验证实际 exe/Node/stdio 链，收到 `initialize` 结果后报告 ready | 没有发送 `initialized`，也未验证后续 RPC、真实桌面启动、proxy/daemon 或增强功能；探针关闭了上下文拓展和新聊天默认预算 |
| `src/windows-integration.mjs` | 启用前执行探针；修改配置失败时回滚；关闭接入保留其他配置 | 这里的启用流程本身未按后续桌面/CLI 更新自动使旧探针结果失效；registered/enabled 不能作为真实连接成功证据 |
| `src/runtime-selection.mjs` | 尝试选用调用桌面所附带的运行时，否则使用 fallback | 路径布局变化或识别失败时，需要明确实际选中谁；fallback 不应被当作已经验证兼容的桌面内置 CLI |
| `src/runtime-fix.mjs` | 已有补丁包指纹、来源与校验、精确基础版本匹配；默认禁止补丁运行时 | 这套保护针对补丁运行时，不能据此认为一般桥接也已有同等级的更新保护 |
| `src/context-ceiling.mjs` | 读模型缓存，生成派生目录并注入启动参数；失败可返回 null | 文件可解析不等于字段语义兼容；新模型和新目录结构应单独验证增强资格 |
| `src/bridge.mjs` | 已对部分未知/非对象消息透传；会改写或准备部分 thread/turn 请求 | 新字段可能在增强操作中遗漏；内部 RPC、重建会话及队列流程需要契约回归 |

## 官方接口能提供哪些依据

OpenAI 的 [App Server 文档](https://learn.chatgpt.com/docs/app-server)说明：连接需要完成初始化握手；可从实际 CLI 生成对应版本的协议 schema；实验接口需要显式启用。由此建议把握手、schema 和实验能力作为验证项。

边界：这份公开接口文档不能证明桌面版未来始终使用相同的启动参数、内部启动策略或进程拓扑，也不能证明修改模型目录会提高服务端实际接受的上下文容量。下列降级、熔断、测试策略均为本项目工程建议，并非 OpenAI 提供的兼容性保证。

## 建议一：严格识别增强入口，其余交给原生 CLI（P0）

只对已确认的直接 stdio app-server 形态启用 Bridge。子命令、选项和选项值必须按位置和参数规则识别，不再依赖 `args.includes()` 判断整个命令。

- `proxy`、`daemon`、帮助、schema 生成和其他维护命令：原参数、原环境、原工作目录与标准流透传，不注入模型目录，不套用直接 stdio 生命周期。
- 新子命令、未知选项、缺少值、重复或歧义 listen 参数：保守透传。新增参数经过验证后再允许进入增强路径。
- 选项值中恰好出现 `proxy` 或 `app-server`，不应改变命令分类。
- 透传保留 stdout 字节、stderr、退出码及平台可实现的终止语义；包装器日志只进入诊断日志或 stderr。
- 原生路径必须避免再次指向 shim，并防止递归启动；无法解析原生程序时报告具体路径问题。

取舍：上游新增一个无害参数时，增强功能可能暂时不可用，但客户端应继续工作。仅维护更长的排除列表无法解决这类未来风险。

## 建议二：更新后重新取得兼容性证据（P0）

将“版本号格式能识别”和“增强能力已验证”分开。缓存兼容性结果时，建议关联以下身份：桌面版本与渠道（可取得时）、实际 CLI 规范路径及文件指纹、CLI 版本、平台/架构、管理器版本，以及正在启用的增强配置和目录结构摘要。

任何相关身份变化都使原来的增强验证失效。启动关键路径只做轻量检查；必要的文件哈希和隔离探针提前或后台执行，不应每次都增加一次可能等待 30 秒的阻塞探针。检测到升级中途文件变化时，放弃本次增强验证，下一次稳定后重试。

建议状态为：待验证 → 隔离验证 → 已验证，或者待验证/失败 → 原生模式。失败保存原因并暂停自动启用；用户手动重试或运行时/管理器身份改变后才重新验证，避免反复启动失败。

“用户希望开启”与“本次有效模式”分别保存。原生模式应展示：Codex 可用，接入增强暂停，原因和恢复入口明确；不能显示成有效连接。

## 建议三：明确自动降级的安全边界（P0）

**优先在生产连接开始前决定本次模式。** 隔离探针通过后再启用增强；未通过则从一开始就运行原生程序。

| 出错时机 | 建议行为 |
| --- | --- |
| 原生子进程尚未启动、客户端数据尚未被消费 | 放弃增强准备，使用原始参数启动原生程序 |
| 已开始握手或转发协议 | 不假设可以无损换进程；保留诊断、清理自己拥有的进程，为下次启动选择原生模式 |
| 已发送 `turn/start`、工具操作或队列任务 | 禁止自动重放；请求可能已经执行，重放可能造成重复修改 |
| 管理器统计/服务失效 | 尽量保持原生协议转发；暂停依赖该服务的增强；尚未提交的增强操作应返回明确错误 |

降级不能悄悄绕过用户明确设置的预算约束，也不能修改组织策略、权限或沙箱。需要修改既有启动覆盖时，只恢复管理器拥有且当前值仍匹配的记录，保留外部改动。关闭接入后仍需核对现有父进程继承的环境，不能只读注册表就断言本次启动已恢复。

## 建议四：把增强功能拆成独立兼容门槛（P1）

基础协议转发、统计、预算修改、新聊天默认预算、上下文拓展、自动队列分别记录验证结果。一项不兼容，先暂停该项；不能依靠一次 `initialize` 成功来开放全部增强。

- 对未知请求、通知和新增字段保持转发。改写请求时优先合并原始对象；确需重建的请求应专门验证字段保留。
- 内部 RPC 使用独立请求 ID、超时和清理；不能吞掉客户端响应，不能在已有连接重复初始化。
- 由管理器自己创建的探针按需要选择稳定/实验能力；透传桌面客户端的能力声明，不擅自删除或扩大。
- schema 差异检查只针对项目使用或改写的接口分类评估；新增无关字段不应让整个客户端不可用。
- 不把远端模型目录变化等同于本地 CLI 更新：模型数据变化也应使相关预算/拓展验证失效。
- 新模型、窗口字段缺失、类型变化或能力无法确认时，不套用旧模型预算或统一拓展上限。保留原生目录，显示能力待确认。
- 本地“目录已加载”“配置已写入”与“实际运行时读回并生效”继续分开；真实能力无法确认时不承诺拓展可用。

## 建议五：生命周期与日志可直接定位问题（P1）

分别记录 stdin EOF、stdin close、输入错误、stdout 关闭/错误、父进程消失、wrapper 退出、EOF 超时以及原生退出。包含 elapsed、父子 PID、已收发字节数、退出码/信号、命令分类和模式选择原因。

参数日志只保留白名单结构：命令层级、已知选项名、传输类型；配置值、socket 细节与路径按需脱敏。不要直接写入完整 argv、环境变量、协议正文或聊天内容。

清理仅针对本次拥有的进程；父进程状态未知不视为已死亡。EOF 的等待时限要区分直接服务器、短命命令和其他进程角色。Windows 与 macOS 分别验证终止和输出排空行为，不能将 Windows 的 `SIGTERM` 调用等同于 Unix 的优雅退出语义。

## 测试和发布门槛（P0/P1）

现有 `.github/workflows/checks.yml` 与 `_build-desktop.yml` 已有核心测试、Windows/macOS 构建与包验证。应在其基础上补充，而不是把当前 CI 描述成没有跨平台检查。

特别注意：`test/integration.test.mjs` 找不到真实 CLI 时会跳过；`test/windows-integration.test.mjs` 使用注入探针验证启用事务。整套测试绿色不能自动证明新桌面版已通过真实启动验收。发布报告必须列出真实运行时路径、版本、平台和跳过项；关键兼容性任务缺少测试二进制应失败或明确判定未验收。

建议新增下列矩阵，全部以隔离配置执行：

| 层级 | 必测场景 | 通过标准 |
| --- | --- | --- |
| 命令分类 | 默认 stdio、两种 listen 写法、proxy、daemon、help、生成命令、未知子命令/选项、歧义参数、值与命令同名 | 只有确定形态进入增强，其余透传 |
| 标准流与生命周期 | 无输入短命命令、EOF 后延迟输出、原生拒绝退出、输出断开、父进程死亡/查询失败、正常退出 | 不截断输出、不重复清理、不残留自有子进程；平台分别验证 |
| 协议契约 | 完整握手、一个无模型推理的只读 RPC、未知通知/字段、字符串和数值 ID、内部 RPC 超时 | 原生响应保留；超时只影响对应增强，不污染连接 |
| 运行时更新 | 旧版→新版、同路径换文件、路径布局变化、预发布版本、版本命令失败、升级后回退、缓存损坏 | 旧验证失效；失败进入原生模式；不自动重复提交 |
| 模型更新 | 新模型 ID、字段缺失/变化、目录刷新、模型切换、旧预算超出新能力 | 无法确认时停用相关修改；保留原生能力 |
| 增强故障 | 服务不可用、目录无法读取/写入、schema 不兼容、队列状态未知 | Codex 基础启动可用；明确展示暂停项；不重放任务 |
| 实际发行包 | exe/Node/CLI 链；macOS 原生启动链；上一支持版本与待支持版本 | 报告实际版本及增强配置；非仅开发态/模拟态通过 |
| 桌面验收 | 完全退出后重开；启动策略读取；进入已有聊天；新建聊天；模型切换 | 无组织设置启动弹窗，出现唯一有效接入；关键增强有读回证据 |

若实际平台没有相应 proxy/daemon 能力，标为不适用并说明证据，不能把模拟通过写成该平台真实验证通过。Windows 本机不能代替 macOS 验收。

建议上游新版本先进入兼容测试，再小范围启用增强，最后扩大启用。普通用户的上游自动更新可能先于维护者验证，因此仍必须有本地保守透传和恢复机制。可另行安排上游变更检查，但本文没有创建任何定时监控。

## 推荐实施顺序与验收交付物

1. **P0，下一轮代码改动优先：**命令严格识别、原生透传回归、日志补足断连原因、完整握手探针。先关闭已知故障入口。
2. **P0，随后：**运行时身份失效机制、生产启动前的模式选择、失败熔断和可见状态；验证恢复只操作自有配置、不重放请求。
3. **P1：**按功能建立能力门槛，补模型/协议更新回归，以及真实 CLI 与桌面验收证据。
4. **P2：**积累各版本兼容记录，完善小范围发布和更新前后的诊断对比；再评估能否减少对桌面内部启动链的拦截。

每轮交付应列出改动范围、真实版本组合、已通过测试、跳过项、Windows/macOS 验证边界、失败时恢复路径。是否允许发布，不能只依据单测数或编译成功。

## 代码实现前可采取的操作

在任务结束后完整退出并重开客户端，以避免内存中的旧 wrapper 继续工作。新版本先检查原生启动，再检查管理器接入及增强读回。若接入导致启动失败，使用管理器已有的关闭接入流程恢复它拥有的启动配置，再确认新启动进程不再继承旧覆盖；不要清空全部用户环境或 hooks。
