# 提前压缩补偿已停用

从 0.25.2 起，Mac 和 Windows 都移除补偿开关，拒绝重新开启，并将旧的开启状态迁移为关闭。原生上下文窗口、压缩阈值、手动压缩和已保存的聊天预算继续保留。

## 为什么停用

原生运行时用于压缩判断的计数可能包含额外的历史推理估算，与界面展示的请求用量不同。运行中追加用户指令会改变历史推理的计数边界。外层补偿只能在安全的轮次边界更新窗口，无法保证整个长轮次都得到对应的补偿。

旧版还存在状态继承缺陷：恢复已经加载的聊天不一定会应用新窗口，但本 App 曾提前丢弃旧补偿记录；关闭开关时也可能错误地认为原窗口已经恢复。0.25.2 保留实际已应用状态、重试未完成的恢复，并把等待恢复明确标成 pending。

因此，920K 是可以配置的目标预算，不是显示用量必定到 900K 才压缩的承诺。关闭补偿也不会移除原生运行时的额外计数规则。此前的短轮次模拟测试只能证明所覆盖的场景，不能作为真实长任务的保证。

## 更新与验证

更新保留原预算，不主动压缩聊天。旧连接在安全的空闲边界恢复原参数；正在运行的 Codex 需正常退出并重开，才能加载新的连接代码。应以实际窗口读回匹配目标为恢复完成，不能只看开关已关闭。

隔离测试继续覆盖旧补偿场景，以验证旧状态恢复。实验入口仅用于测试注入，正式界面和 API 都不能重新开启。

更早的内核补丁仍然停用：它修改官方运行时后失去 Computer Use 所需的签名身份。此次更新不修改官方 Codex 二进制。
