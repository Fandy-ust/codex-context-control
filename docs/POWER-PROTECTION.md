# Local power-loss protection

The shared service enables protection on Windows and macOS while Context Manager is running. It does not make quota or model requests.

Manager JSON writes flush a private temporary file before atomic replacement. Two validated `.safe-1` / `.safe-2` copies retain previous values. Reads recover from the first valid copy and preserve the corrupt primary as `.damaged`. Invalid runtime-fix preferences still disable the optional patched runtime rather than automatically re-enabling an old opt-in. macOS also flushes the parent directory after replacement; Windows flushes file contents before replacement.

Codex protection lives in `power-protection/codex/` under the manager data directory. It protects `config.toml`, `.codex-global-state.json` and native `state_*.sqlite` indexes, including WAL contents through SQLite's online backup API. It excludes credentials, session transcript files and project source files. TOML, JSON, SQLite integrity and backup block checksums are validated.

Every five minutes, changed sources produce a recovery point. Unchanged sources are skipped. Each point has a complete manifest referencing compressed 64 KiB blocks; unchanged blocks are reused without depending on a chain of earlier manifests. Recent and daily tiers use independent block pools, so corruption of a recent block can fall back to a daily copy. Keep the freshest working point plus time-spaced historical points: one per local calendar day in the last seven days, one per Monday-based week from seven to 31 days old, and one per month for older points up to three calendar months. Keep the newest successful point in each bucket. Expired points and unreferenced blocks are removed; the 200 MiB budget also includes quarantined damaged originals and can shorten history if needed. Large source sets whose compressed snapshot would exceed one third of the budget are skipped with an error, preserving existing recovery points. Temporary SQLite staging space is additional while capturing a snapshot.

Automatic recovery only handles files that are missing or fail validation, and only when no Codex desktop, CLI or app-server processes are detected. Pending recovery checks for process exit every five seconds locally. It never stops the app. A second process check immediately before replacement reduces launch races; the app should remain closed during recovery. Valid but empty project lists are not rolled back, since they may be intentional deletions. These can be recovered from the retained snapshots after inspection. The status file records pending files, errors, restored files and current storage use.

Snapshots are stored locally on the same device. Disk flushes and redundant copies reduce power-loss damage but do not guarantee survival of storage hardware failure. The freshest changes since the last successful snapshot may be lost. Historical retention grows over time; installing protection does not create past recovery points.

## Restore from the UI

Open Settings → Backup and restore on Windows or macOS. Each recovery point shows its time, protected files and uncompressed content size; storage used is the actual deduplicated disk use. Select Review and restore, then confirm Close Codex, restore and reopen. This pauses manager queues and cancels scheduled activation before closing Codex desktop and CLI sessions, which interrupts running tasks. Alternatively choose Restore after I exit manually. Queues remain paused after restoration; resume them when ready.

Keep Context Manager running. Recovery points are materialized and fully validated before queueing so rotation cannot remove the selected data. The service waits for a stable process-free interval, checks again before writing, and saves current files plus SQLite sidecars for rollback. It updates both global-state primary and backup, removes stale SQLite sidecars, and verifies restored file hashes and database integrity before reopening Codex. If Codex reappears during restoration, the service stops and waits for a safe rollback. If the service exits mid-write, its persisted journal triggers offline rollback on the next launch, rather than reporting success. Different native database generations are rejected for compatibility review.

Restore changes configuration, project assignments and the chat index; it preserves transcript files and project source code. A snapshot cannot recover changes made after that snapshot. The UI does not close Codex until you confirm a recovery point. The current and previous manual recovery workspaces retain rollback evidence in the local protected directory.
